# Modbus-to-MQTT Bridge (Prototype)

A C-based prototype that reads sensor data via the **Modbus** protocol and
publishes it via **MQTT**, simulating the same core data pipeline used by
industrial IoT gateways (e.g. the Aplex ARiio-5101W running Klemsan's own
`MqttGateway` software).

Built as part of the Klemsan internship, assigned by Mehmet Samğar:
> "Code that reads data via the Modbus protocol and serves that data via
> the MQTT protocol. Design and architecture entirely up to you."

## What it does

1. **`server.c`** — a Modbus TCP simulator standing in for a real device
   (e.g. a Klemsan KLEA energy analyzer). Generates realistic, slightly
   fluctuating values for voltage, current, power factor, and frequency —
   using the same raw-integer scaling convention (`/10`, `/100`, `/1000`)
   as real Modbus energy meters.

2. **`client.c`** — the actual bridge:
   - Connects to the Modbus device and reads holding registers
     (Modbus function code 3)
   - Decodes/scales the raw register values into real-world units
   - Publishes the readings as a JSON payload to an MQTT broker
   - Runs continuously, polling on a configurable interval
   - Handles `Ctrl+C` for clean shutdown
   - **Automatically detects a dropped Modbus connection, closes it, and
     reconnects** — tracks consecutive failure count, retries on the
     configured poll interval, and resumes normal operation the moment
     the device becomes reachable again, with no manual restart needed

3. **`config.txt`** — all connection settings (Modbus IP/port, register
   range, MQTT broker/port/topic, poll interval) are externalized here
   rather than hardcoded, so behavior can be changed without recompiling.

## Architecture decisions

- **Config file over hardcoding**: chosen for flexibility — the same
  compiled binary can point at different devices/brokers just by editing
  `config.txt`.
- **Plain key=value config format**: kept deliberately simple — no extra
  parsing library needed, easy to read/edit by hand, sufficient for the
  current scope.
- **Automatic reconnection over fail-and-give-up**: a failed read closes
  and rebuilds the Modbus connection rather than repeatedly hitting a
  dead socket — mirrors the resilience philosophy of the real system's
  `Restart=always` systemd policy, implemented at the application level.
- **C + libmodbus + libmosquitto**: chosen to stay close to how real
  embedded gateways are typically implemented (matches the language
  discussion with Mehmet Hoca; a Go implementation was explored in
  parallel for comparison).

## Build

Requires `libmodbus-dev` and `libmosquitto-dev`:
```bash
sudo apt install build-essential libmodbus-dev libmosquitto-dev
```

Compile:
```bash
gcc server.c -o server -I/usr/include/modbus -lmodbus
gcc client.c -o client -I/usr/include/modbus -lmodbus -lmosquitto
```

## Run

For local testing, a local Mosquitto broker is recommended (avoids
dependency on external network policy — see Known limitations below):
```bash
sudo apt install -y mosquitto
sudo service mosquitto start
```
Set `mqtt_broker=127.0.0.1` in `config.txt`.

Terminal 1 — start the simulated device:
```bash
./server
```

Terminal 2 (optional) — subscribe to watch messages arrive live:
```bash
mosquitto_sub -h 127.0.0.1 -t "klemsan_intern/armaghan/modbus_readings"
```

Terminal 3 — start the bridge:
```bash
./client
```

Edit `config.txt` and rerun `./client` (no recompiling needed) to change
broker, topic, poll interval, or target device.

## Verification

- **End-to-end data flow**: readings generated by `server.c` were read via
  Modbus, published via MQTT, and independently received by a separate
  `mosquitto_sub` subscriber — confirming the full pipeline works, both
  against a real public broker (`test.mosquitto.org`) and a local broker.
- **Fault tolerance**: the Modbus server was killed and restarted multiple
  times while the client was running. The client correctly detected each
  failure (`Connection reset by peer`, `Invalid argument`), retried on
  schedule without crashing or hanging, and automatically resumed normal
  publishing the moment the server came back — verified across 7+
  consecutive failures in one test run.

## Known limitations / next steps

- Currently tested against a Modbus **simulator**, not real hardware
- Encrypted (port 8883) and in some cases unencrypted (port 1883) MQTT
  traffic to external brokers has been observed to be inconsistently
  blocked on the ODTÜ Teknokent network; a local Mosquitto broker is used
  as a reliable workaround for development/testing
- No TLS/authentication implemented yet (real system uses
  `ssl://ems.kioplatform.com:8883`)
- No persistent logging (real system logs to `logs/basic`,
  `logs/communicationStatistic`, etc. — a pattern worth replicating)
- MQTT-side reconnection (if the broker connection drops) not yet
  implemented — only Modbus-side reconnection is currently handled
